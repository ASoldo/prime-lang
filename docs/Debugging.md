# Tracing the Prime interpreter

Run `prime-lang schema trace` to get the machine-readable contract from the installed CLI. [Version 1 JSON Schema](schemas/trace-v1.json)

`prime-lang run --trace TARGET` executes the program and writes a call record to stderr each time the interpreter enters a named Prime function. Program output still goes to stdout. The command exits with status 0 on success and 1 on a reported runtime error. It works with source paths and manifest module names.

Save this program as `demo.prime`.

```prime
module demo;
fn twice(x: int32) -> int32 { x + x }
fn main() { out(twice(21)); }
```

```sh
prime-lang run --trace demo.prime 2>calls.ndjson
```

The program prints `42`. For a file at `/tmp/demo.prime`, the trace contains these two records.

```jsonl
{"schema_version":1,"event":"call","module":"demo","function":"main","path":"/tmp/demo.prime","depth":0,"start":54,"end":58}
{"schema_version":1,"event":"call","module":"demo","function":"twice","path":"/tmp/demo.prime","depth":1,"start":16,"end":21}
```

## Reading the trace

Each trace record is one UTF-8 JSON object followed by a newline. Readers can select records by `schema_version` and `event`. Front-end diagnostics and explicitly enabled subsystem debug logs use their usual stderr formats.

| Field | Meaning |
| --- | --- |
| `schema_version` | Integer format version, currently 1. |
| `event` | `call` for entry into a named Prime function, `warning` for interpreter deprecations, or `runtime_error` for a terminal interpreter error. |
| `module`, `function` | Defining module and function name for a call. Built-ins and anonymous closures produce no call record. |
| `path` | Source file containing the function declaration, including declarations generated from another module’s item macro. An in-memory stdin module uses `<stdin>`. |
| `start`, `end` | Zero-based UTF-8 byte offsets for the function name in the parsed definition, including `start` and excluding `end`. Functions generated by item macros use the name in the macro definition. |
| `depth` | Number of enclosing module evaluation frames on the current interpreter thread. Top-level `main` has depth 0. Constant initialization also establishes a frame. |
| `message` | Diagnostic text for a warning or runtime error, including available Prime stack frames for an error. |
| `frames` | Array on `runtime_error`, innermost frame first. Each object contains `path`, qualified `function`, and half-open UTF-8 byte offsets `start` and `end`. The array is empty when the interpreter has no Prime frame. |

Calls on one interpreter thread appear in execution order. Calls in independently scheduled tasks can interleave, and each worker starts its own depth count. This trace covers interpreted execution. Native executables and firmware have their own execution environments.

## Locating a runtime error

Change the body of `twice` to `x / (x - x)` and run `prime-lang run demo.prime`. The diagnostic identifies integer division by zero, then lists the failing expression in `demo::twice` and its call site in `demo::main`. Each frame has a path and a half-open UTF-8 byte range. A failure outside expression evaluation falls back to the declaration range. Expressions expanded from macros retain their AST offsets, which may originate in a macro body. The same diagnostic appears in the final JSON record when tracing is enabled.
